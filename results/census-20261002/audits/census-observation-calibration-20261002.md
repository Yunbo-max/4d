# Observation calibration audit — 2026-10-02

Read-only local audit; no SSH, GPU, tracker implementation, or projection experiment. Nine findings:

1. **The GT camera convention is explicit, not a guess.** `actionmesh/repo/actionbench/README.md:19` and the cached official `work/actionmesh-prep/actionbench-smoke/projection.py:31` specify `X_cam = X @ R.T + T`, Blender camera looking along **−Z**. Set depth `d=-X_cam.z`; `u=W/2*(1+fx*X_cam.x/d+ppx)`, `v=H/2*(1-fy*X_cam.y/d-ppy)` for the original square frames. Here 512 pixels and focal NDC 2.1875 imply focal length 560 pixels. The provided R/T belong to **GT world coordinates**, not automatically to the model's canonical coordinates.

2. **The next CPU camera check is cheap and evaluation-only.** Project the original GT XYZ at frames 0, 8 and 15 onto the corresponding original 512×512 RGBA images; reject/report nonpositive-depth points rather than letting the example script's depth clipping hide them. Save point overlays, fraction in bounds, fraction landing inside alpha>127, and distance-to-mask median/p95. If using a point-splat silhouette or z-buffer, freeze radius/tolerance and report sampling holes; point-cloud mask IoU is not an exact mesh-render IoU. This tests transpose/sign/frame-index/camera conventions. It does not calibrate a prediction, estimate a guidance camera, or establish a learned method result.

3. **Independent recropping is ruled out for these two runs.** Both retained `preprocessing.json` files have `independent_cropping=false` and one identical image transform over all 16 frames. Mannequin: source→processed `(u+20,v−39)`, size 451×451. Bat: `(u−73,v−82)`, size **387×386**, not exactly square because integer padding rounds. Any observation loss in processed pixels must compose this recorded transform; if using encoder pixels, also account for the loaded `BitImageProcessor` resize/crop. Its exact runtime config has not been inspected here. The simplest calibration check uses original 512×512 observations and avoids that extra coordinate transform.

4. **No native calibrated prediction-to-input camera was found.** Inspected `TripoSGPipeline.__call__`, `encode_image`, the ActionMesh TripoSG wrapper and inference script expose image conditioning and canonical mesh extraction, but no input-camera argument, estimated camera output, or saved canonical→input transform. This is evidence of a missing exposed calibration interface, not a claim that the trained prior has no orientation bias. The extraction bounds ±1.005 establish only coordinate extent, not input-view extrinsics.

5. **The viewer cameras are not evidence of registration.** `actionmesh/render/visualizer.py:78` chooses `get_uniform_camera(distance=3.0)` and fixed views U000/U004/U008. These are presentation views. The camera conversion utilities in `render/cameras.py` are useful when a transform is actually known; a plausible default front render cannot establish which view matches the source image.

6. **The GT-anchor ICP matrix is forbidden as a guidance calibration shortcut.** It was fitted from GT 3D positions and includes anisotropic scale. Composing it with `camera.json` would make a GT-dependent renderer. It remains legitimate for labeled evaluation diagnostics only. Even using supplied camera metadata requires stating a calibrated-input assumption; arbitrary user images/text-generated videos do not necessarily provide it. An input-guided method must estimate its effective camera/pose using the input image(s), predicted anchor, and only metadata declared available at inference.

7. **A legitimate input-only baseline is frame-zero silhouette registration with the anchor frozen.** Render the predicted anchor and minimize a fixed mask overlap/boundary-distance objective against input alpha, using bounded multiple pose starts and one shared perspective camera. With fixed input focal length, optimize rigid pose/depth and image offset; fix the object-scale gauge rather than jointly allowing unidentifiable free scale and depth. Avoid anisotropic deformation during calibration. Freeze the selected camera for all subsequent frames. Report initial and final silhouette error, pose hypotheses, runner-up ambiguity, clipping/depth checks, and camera-only improvement before adding any latent/query steering. If only silhouettes are used, symmetric front/back or tangent-motion ambiguities remain; a low mask error is not proof of correct material registration.

8. **There is a concrete go/no-go barrier before steering.** First validate GT projection as an evaluation convention. Then obtain an input-only registration that explains the original anchor silhouette without reading GT positions, ICP matrices, or future GT tracks. Render the unchanged sequence with that fixed registration and show its errors. If silhouette registration has several indistinguishable poses or cannot fit the anchor, a track-energy gradient has an unreliable coordinate basis; do not present a GT-aligned optimizer as an inference-time method. Registration cost and its independent benefit are part of the baseline budget.

9. **Tracking is secondary to calibration and observability.** Installed OpenCV makes LK feasible, but uniform surfaces and contours suffer from the aperture problem, occlusion and changing visibility. Contour flow is not automatically material-point motion. Only after registration should input tracks be checked for texture support, forward/backward consistency, visibility and held-out endpoint accuracy. No tracker is implemented or run in this audit. Silhouette energies can constrain shape while leaving tangential material motion unidentifiable, so they cannot alone support the desired claim about material-motion steering.
